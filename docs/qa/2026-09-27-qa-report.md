# flowline v1 — QA report (2026-09-27)

## 1. Summary

Task 20 QA'd flowline from two angles, both exploratory: a developer-experience
(DX) pass by a developer embedding flowline in a CRM, and an operator (ops)
pass by a non-technical CRM user driving the editor and run viewer through
the `examples/mini-crm` UI. A third stream, Task 20-E2E, is an automated
Playwright regression suite added afterwards to lock in the flows the
exploratory passes exercised; it is a check against regressions, not a
substitute for exploratory QA.

Exploratory QA found bugs by using the product the way a real user would —
building real workflows, mistyping things, resizing windows, sending
concurrent webhooks — rather than asserting known-good behavior. The e2e
suite instead pins six specific scenarios (build, publish, stale ref, a full
webhook → approval → outbox round trip, reject, and a loop stepper) so they
can't silently regress.

## 2. Method

- **Charters.** Two personas drove the exploratory rounds:
  - **DX** (`task-20-dx-qa.md`): a developer embedding flowline in a CRM,
    building a plugin, nodes, a sub-flow and a webhook workflow, and
    checking the README/guide/TSDoc against real behavior with `tsc` probes
    and headless runs.
  - **Ops** (`task-20-ops-qa.md`): a CRM ops person using only the
    `examples/mini-crm` UI, benchmarked against `docs/research/canvas-ux.md`
    (Activepieces, Zapier, n8n, Make patterns).
- **Environments.** DX QA ran in a scratch project outside the repo against
  packed tarballs (to exercise `publishConfig`/dist exports as a real
  consumer would), on Node 22.14, pnpm 10.5.2, TypeScript 5.9.3, zod 4.6.5,
  a temporary Postgres 17 cluster, and headless Playwright screenshots. Ops
  QA ran mini-crm's own server/web app (ports 8911/5411) driven by headless
  Chromium/Playwright 1.62.1 at 1440×900.
- **This is exploratory QA, not tests.** Both rounds are charter-driven
  investigation against the running product and its docs — deliberately
  unscripted, looking for surprises — distinct from the unit/integration
  test suites (`pnpm test`) and from the automated e2e suite described in
  §7, which pins specific scenarios after the fact.
- **Fix batches.** Findings were triaged into fix batches, each gated by
  `pnpm test`, `pnpm -r typecheck`, `pnpm lint` and `pnpm build`, all
  required to exit 0:
  - `lib-batch-c-report.md` — DX QA fixes (H1–H3, M1–M9, L1–L13).
  - `batch-d1-report.md` — ops QA editor/canvas/panel fixes (H1–H3, M2–M8,
    M12–M14, M17, and related Lows). Two fix rounds; merged `267e8de` after
    the r3 re-review closed all four remaining findings
    (`batch-d1-r3-review.md`).
  - `batch-d2-report.md` — ops QA run-viewer/run-list/mini-crm-page fixes
    (M1, M9–M11, M15–M16, and related Lows). Merged.

## 5. Known issues

Every unfixed Low, and any deferred Medium, with a one-line rationale. (No
Medium findings remain unfixed — see §3.)

- **DX L6** — branch keys in the builder are untyped. Ruling 72: typing
  polish with low payoff; the validator already catches it with a clear
  message.
- **DX L7** — `DeepExpr` allows refs in fields where they make no sense.
  Ruling 72: autocomplete noise only; the validator rejects them where
  `literalOnly` applies.
- **DX L9** — an object passed to a `z.string()` field is only a warning,
  not an error. Ruling 72: promoting this to an error changes validation
  semantics editor drafts rely on (publish-then-fix); deferred pending a
  controller ruling.
- **DX L12** — `@flowline/react` exports layout internals (`BRANCH_GAP`,
  `CARD_W`, `useShallow`, …). Ruling 72: removing them is a breaking API
  change, deferred to a later API sweep.
- **Ops L16** — auto-generated step IDs are cut mid-word at 48 characters.
  Out of scope for batch D1 (the code is in mini-crm's `workflows.tsx`,
  which that batch was told not to touch).
- **Ops L18 (partial)** — toast overlap and "Failed to fetch" copy were
  fixed, but automatic recovery once the server comes back was not
  implemented.
- **Ops L23** — no local draft recovery after a reload. Ruling 76:
  workflow docs can carry customer PII, so writing drafts to `localStorage`
  was rejected; `beforeunload` plus the router-blocker dialog (H2) cover
  the loss case instead.
- **Ops L27** — a Transform output field's accessible name changes once
  you type a name into it. The original report noted this as expected,
  screen-reader-only behavior, not a bug; no change was made.
- **D1 follow-up** — Tab from the panel's last field wraps to the app nav
  instead of stopping at the end of the panel. Carried over from the

  fixed.
- **D1 follow-up** — a step ID that is assembled dynamically in code (for
  example `` steps[`${p}Request`] ``) can't be tracked by rename or

- **D1 follow-up** — `labels.stepDeleted` changed from a `string` to a

- **E2E-L1** — a benign `ResizeObserver loop` console error appears once

- **E2E-L2** — step-picker search still fuzzy-matches unrelated steps for

## 7. E2E suite

The Playwright suite (`examples/mini-crm/e2e/`) covers the scenarios most
exercised by exploratory QA, as automated regressions:

- **Build flow** — new workflow, add a step, fix a missing-ref issue via
  the data picker, save, publish, and confirm the list shows the live
  version.
- **Stale reference** — deleting a step that another step refs, confirming
  the issue pill, field-level error, blocked publish (client and server),
  and that undo restores a publishable state.
- **Webhook → approval → outbox** — send a webhook lead, follow it to a
  waiting run, approve it from the Approvals page, and confirm the run
  completes and exactly one outbox email links back to the run.
- **Reject → Stopped** — reject an approval from the run's approval bar
  and confirm the stopped banner, empty outbox, and the Stopped filter.
- **Generic resume refuses a host-handled approval** — `POST
  /flowline/runs/:id/resume` returns 409 `resume_host_handled` for an
  approval step, while the CRM's own approval bar still works.
- **Loop stepper and inspector tabs** — a `forEach` → `transform` run,
  stepping through iterations with Previous/Next and checking the Input,
  Output, Error and Timeline tabs.

Build the packages, then run the suite:

```
pnpm build && pnpm --filter @flowline/example-mini-crm e2e
```

Each server (Hono API and Vite) is started fresh per run with in-memory
storage and reset via `POST /api/demo/reset` before each test, so results
are deterministic; there are no sleeps or `waitForTimeout` calls, only
web-first assertions. As of batch D1's merge into `flowline-v1` (`267e8de`),
the suite passed 10/10 with all project gates (`pnpm test`, `pnpm -r
typecheck`, `pnpm lint`, `pnpm build`) green.
